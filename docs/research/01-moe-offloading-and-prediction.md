## 2. What actually matters for a 4060 laptop with NVMe

**Expert sizes** (params = 3 x hidden x moe_intermediate; from public HF configs, verify against the actual checkpoints; Q4 ~4.5 bit/param incl. scales):

| Model | routed experts/MoE layer, top-k, MoE layers | params/expert | Q4 size | expert fetches/token | bytes/token if nothing cached (Q4) |
|---|---|---|---|---|---|
| OLMoE-1B-7B | 64, 8, 16 | 6.3M | ~3.5 MB | 128 | ~0.45 GB |
| Qwen3-30B-A3B | 128, 8, 48 | 4.7M | ~2.7 MB | 384 | ~1.0 GB |
| Mixtral 8x7B | 8, 2, 32 | 176M | ~99 MB | 64 | ~6.3 GB |
| DeepSeek-V3 / Kimi-K2 class | 256-384, 8, ~58-60 | 44M | ~25 MB (FP8 44 MB) | ~470 | ~11.6 GB (FP8 ~20 GB) |
| Qwen3-235B-A22B | 128, 8, 94 | 18.9M | ~10.6 MB | 752 | ~8 GB |
| GLM-4.5 355B class | 160, 8, ~89 | 23.6M | ~13 MB | ~712 | ~9.4 GB |

**Bandwidth ceilings.** RTX 4060 Laptop is PCIe 4.0 x8 -> ~16 GB/s theoretical, ~12-13 GB/s achievable H2D with pinned memory. Gen4 laptop NVMe: 5-7 GB/s sequential; expect 3.5-5 GB/s sustained with 10-50 MB O_DIRECT reads at QD>=4 (SSD-LLaMA reached 77.7% of peak with io_uring + packed layout; naive paths 43%). Under Windows the equivalent is overlapped/IOCP `FILE_FLAG_NO_BUFFERING` reads (or DirectStorage) - measure it first. DDR5 dual-channel CPU bandwidth (~50-70 GB/s) is 4-5x PCIe, so experts already resident in RAM can be **computed on the CPU** (DAOP/Fiddler idea) instead of copied when the GPU cache misses - an exact-preserving option to evaluate.

**Consequence: 500B-class decode is SSD-bandwidth-bound, not compute-bound.**
tok/s ~= SSD_BW / (bytes_per_token x (1 - hit_rate)).
- Qwen3-235B Q4 (8 GB/token): with 4.5 GB/s and hit 30% -> ~0.8 tok/s; hit 50% -> ~1.1; hit 70% -> ~1.9.
- DeepSeek/Kimi Q4 (11.6 GB/token): hit 30% -> ~0.55 tok/s; hit 50% -> ~0.8.
- Our cache is tiny: ~3.5-4 GB VRAM (after attention/shared weights/KV) + ~6-8 GB pinned RAM = ~10 GB, i.e. 2-4% of a 250-350 GB model. Reference points: SGLang Kimi-K3 (0.5-2% cache) gets 17-23% hit; DeepSeek-V4-Flash at 15% cache gets 46-80%; Qwen3-30B at 13% budget: LRU 65.9% (oracle 79.1%). Expect ~20-35% hit at 500B scale (extrapolation, must be simulated). So: ~0.5-1 tok/s is the realistic band for a 500B model; 100-300B MoE at Q4 fits much better.
- Prefetching does **not** reduce bytes; it only hides latency. Per-layer GPU compute at batch 1 is ~1-3 ms, while one 13-25 MB expert read takes 3-6 ms at 4.5 GB/s; a layer's ~8 experts need 25-50 ms of SSD time. When SSD is saturated the token time is the summed byte time whether or not prefetch is perfect. Value of prefetch = keep the SSD queue full during compute (utilisation), not less traffic. Therefore **false prefetches are directly harmful** (they burn the scarce resource): precision matters as much as recall; use a byte budget.
- Utilisation target: aim for >75% of measured peak SSD BW (SSD-LLaMA 77.7%), then attack bytes/token.
- Bytes-reduction levers ranked: (1) hit rate (LRU-like policy, tiering), (2) smaller resident format (Q4/Q5 experts are the "model", quality decision, not caching), (3) lossless entropy coding of stored experts (rANS -33% on their stored format; costs GPU/CPU decode - test on our format), (4) lossy substitution (HOBBIT, gated behind measurement).

**Locality numbers for simulator calibration** (all from the sources above):
- Qwen3-30B-A3B (48 layers, 128 experts, top-8): P(expert reused at next token)=0.444 vs their "chance" 0.223 (their definition; note plain 8/128=0.0625, so define chance explicitly in our sim); 95% of routed traffic in 52.5% of experts; at 13.4% budget: LRU 65.9%, LFU 60.1%, static pinning 59.2%, Belady 79.1%. Code experts nearly disjoint from prose/math (Jaccard 0.11-0.16 vs 0.33-0.42 among general/math/medical).
- Kimi-class 896 experts/layer: cross-domain Jaccard as low as 0.066; LRU ~70% of Belady at 32 experts/layer; frequency tables ~33% of Belady and degrade on domain shift.
- MoE-Infinity: within one request <5% of experts repeatedly used (100-expert models), Mixtral ~25%; skewed within a request, flat across requests (so global frequency tables are weak; per-session state is strong).
- SSD-LLaMA/SGLang: skewed within a prompt, identities change across prompts; real hit rates 17-80% depending on cache/model ratio (see table above).
- Prediction accuracy vs lead: 1 layer ahead 90-97%, 2-3 layers ~90% (HOBBIT), 8 layers ahead 54% for naive skip vs better for learned (ProMoE); shallow layers ~70% (Fate); pre-attention same-layer 93-98% (trained).
- Gap to Belady for online policies is stable at ~44-46% (Reproducible Eval), and simple next-use predictors close little of it: do not expect a clever policy to beat LRU-ish by large margins.
- Not found: published per-layer entropy / co-activation numbers for GLM/Kimi/DeepSeek-V3 decode traces; we must record our own (section 3).

## 3. Decisions for LM Atomic

**Storage/I/O first (biggest measured win, no prediction needed).**
1. Expert-pack file: one contiguous (gate|up|down + scales) block per (layer, expert), 4 KB (preferably 64 KB) aligned, single direct read per expert. Windows: unbuffered overlapped I/O with multiple in flight (QD 4-16), reading into pinned staging buffers, `cudaMemcpyAsync` on a copy stream, events for readiness; benchmark DirectStorage as an alternative. Bypass the OS page cache (SGLang: removing cache->pinned copy is a key gain). Reuse: SGLang (Apache-2.0) and llama.cpp (MIT) for ideas/code; SSD-LLaMA has no separately licensed code confirmed.
2. Three tiers: VRAM cache (GPU-resident slots) - pinned RAM cache - NVMe. Fixed-size slot arenas per tier (equal expert sizes per model), no dynamic allocation in the hot path.

**Cache policy.**
3. Baseline = per-tier LRU (validated by SSD-LLaMA, SGLang, kernel-tiering paper; robust to domain shift). Add only what the simulator shows beats it: (a) layer-aware weighting with shallow-layer bias (MoE-Infinity, Fate; first layers have the least reliable prefetch), (b) a second-chance/frequency guard (2Q/SLRU/ARC-style, cf. HOBBIT's LRU+LFU mix) to stop one-off experts from evicting the session's hot set, (c) per-layer capacity allocation by DP over measured per-layer hit curves (AdapMoE). Static frequency pinning: skip (weak under domain shift).
4. Promotion rule VRAM<-RAM: promote on second use within a window (break-even ~1.06 reuses per kernel-tiering paper); RAM tier is filled on SSD read; evictions from VRAM demote to RAM (victim cache).
5. Skip request-level EAM matching (MoE-Infinity) in v1; implement it as a simulator-only comparator - with 3% residency and one user session, its extra signal likely matters less than raw policy sanity. Revisit if simulator shows >5 pts over LRU.

**Predictor (staged, all Exact-safe: predictions may only trigger prefetch; the real router always decides).**
6. P0: no predictor (matches SSD-LLaMA); measure stall/utilisation.
7. P1 (training-free, cost ~ one router GEMV d x E, e.g. 7168x256 ~ 1.8M MAC): run router(l+1..l+D) on the current layer's residual/gate input (Fate, HOBBIT, AdapMoE, DALI residual). Inputs: hidden state entering layer l's MoE block, next layers' router weights, router logits margin. Rank candidates; prefetch top-(k+delta) where delta is chosen from the logit margin/entropy (APEX-style, calibrated online) with a per-token byte budget and a lookahead D of 1-3 layers only (accuracy drops with depth; SSD latency of 3-6 ms per expert means D>=2 is needed to cover it).
8. P2 (optional, needs offline training on our own router traces): pre-attention linear predictor (2 linear maps + ranking loss; 93-98% same-layer, also fixes layer 0/1) - gives lead time of one attention block (~ms), which is too short for SSD but fine for RAM->VRAM promotion. Only pursue if P1 recall <85% in the simulator.
9. Per-session adaptation: no weight training at runtime. Adapt only (a) delta/threshold per layer from a running estimate of precision/recall, (b) a small per-session history table (last-token experts per layer, ST-MoE style) as an extra candidate source that bumps recency. Skip: learned MLP predictors per layer (ProMoE, ExpertFlow transformer predictor), sequence models (SeqMoE), Pre-gated MoE (retrains model), router fine-tuning (ReMoE, cache-aware routers), token regrouping/batching (Klotski, MoE-Lightning, MoE-Gen, ExpertFlow: batch=1 target), speculative-decoding-based prefetch (union of experts over draft tokens inflates traffic), SwapMoE/AdapMoE expert-count reduction (changes outputs).

**Prefetch scheduling.**
10. Two I/O queues: demand (priority, never queued behind prefetch) and prefetch (best effort, cancellable if not yet started). Cap outstanding prefetch bytes (start: <=40% of measured SSD BW window). Order by predicted probability x (1 - layer distance decay). Do not prefetch into VRAM directly from SSD if it would evict an entry with higher reuse score; stage into RAM tier first, promote just-in-time.
11. Prefetch what is missing only after checking VRAM then RAM; mark entries "prefetched-unused" so they are first eviction victims (bounds pollution).
12. CPU-execute path (exact): if the expert is RAM-resident and the GPU slot is not, compute on CPU when (bytes / PCIe BW) > CPU-compute time; evaluate in the simulator before building.

**Near-lossless (optional, measured only, disabled in Exact).** HOBBIT-style low-precision substitution on a miss for low-gate-weight experts (their claim: ~30% of misses -> int4, <=1% task loss on Mixtral/Phi-MoE). Gate it behind a KL/perplexity + task-suite gate against the Exact reference; keep it off in reference runs.

**Measurement (implement in both simulator and runtime with the same definitions).**
- Trace format: per token, per layer: chosen experts, router logits (top-16), timestamps of demand issue/complete, prefetch issue/complete, tier of service (VRAM/RAM/SSD/CPU-exec), bytes read.
- For each prefetch decision at (layer l, issue time t_i, lookahead D): P = prefetched set, A = actual routed set. Recall = |P n A|/|A|; precision = |P n A|/|P|; "useful-byte ratio" = bytes later used before eviction / bytes prefetched; wasted SSD bytes/token; miss-late count (arrived after demand: partial credit); lead time = t_demand(l) - t_ready(expert) (negative = stall; report distribution p50/p90); stall ms/token; SSD BW utilisation; tokens/s.
- Report per layer and per lookahead depth, per domain (code/prose/math) - locality differs (Jaccard 0.11-0.42).
- Simulator replay: follow Reproducible Eval - replay in true token/layer order, separate prompts, flush or warm-start explicitly, avoid identical-prefix templates, report gap to Belady at the same capacity, and run capacity sweeps 1-30% of experts. Calibrate against the numbers in section 2 (e.g. Qwen3-30B LRU 65.9% @13.4%). Record real traces from OLMoE (already served locally), Qwen3-30B-A3B and the synthetic-GLM harness first; validate simulator hit-rate within a few points of the runtime on the same trace before trusting 500B projections.
- Acceptance thresholds: a predictor is kept only if it raises tokens/s (not just recall) at equal SSD BW and precision >= ~50% at the chosen delta; otherwise cut delta.
